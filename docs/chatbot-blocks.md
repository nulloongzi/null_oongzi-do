# 카카오 챗봇 스킬·블록 현황

운영자가 카카오톡 챗봇으로 처리하는 관리 작업의 전체 목록이다.
최초 설정(인증 4종)은 `kakao-openbuilder-setup-prompt.md` 에 있고, 그 뒤 늘어난
팀·신고·클레임은 여기에 모은다.

콘솔 주소: https://chatbot.kakao.com
스킬 URL 은 모두 `https://us-central1-nulloongzi-do.cloudfunctions.net/<함수명>` · POST.

## 챗봇의 역할 (2026-09-16 재정립)

챗봇은 **두 얼굴**이다. 같은 봇이지만 쓰는 사람이 다르다.

| | 누가 | 무엇을 |
|---|---|---|
| **관리 창구** | 운영자만 | 인증·팀·신고·관리자·클레임 처리 |
| **소통 창구** | 누구나 | 지도로 데려다주기, 제보 받기 |

### 챗봇이 하지 않는 것

**지도를 흉내내지 않는다.** 팀 검색·목록·상세는 앱과 웹이 훨씬 잘한다. 카톡 안에서
그걸 다시 만들면 더 나쁜 지도가 하나 더 생길 뿐이다.

챗봇이 유일하게 더 잘하는 건 두 가지다:

1. **앱을 안 깐 사람을 지도까지 데려다주는 것** — 인스타 → 채널 → 지도 로 이어지는
   깔때기의 가운데 토막. 설치 없이 한 번에 넘어간다.
2. **앱 없이 제보를 받는 것** — 인앱 신고는 로그인이 필요하다. 지나가다 "여기 정보
   틀렸는데" 하고 알려주는 사람은 그 문턱을 넘지 않는다.

랭킹·후기·팀 추천·챗봇 내 커뮤니티는 만들지 않는다 —
`PHILOSOPHY.md` 가치 필터 #1(접근성 > 위상)·#4(지도가 wedge)에 걸린다.

## 보안 — 두 층으로 막는다

```
요청 도착
   ↓
① 스킬 키    이 호출이 카카오에서 온 게 맞나   → 아니면 401 (말풍선 없이 끊는다)
   ↓
② 관리자     이 사람이 운영자인가              → 관리 발화만 검사
   ↓
처리
```

**①이 왜 필요한가.** 스킬 URL 은 `invoker: "public"` 이다(카카오가 불러야 하니
어쩔 수 없다). 그런데 ②만 있던 동안은 본문에 실린 `user.id` 만 봤다. 이 레포는
공개라 주소도 본문 형식도 다 공개돼 있으니, **운영자의 카카오 user id 만 알면
누구나 팀 삭제·관리자 승인·소유권 이전을 할 수 있었다.** 더 나쁜 건 그 id 가
카카오가 정하는 값이라 새어도 바꿀 수가 없다는 점이다.

`CHATBOT_SKILL_KEY` 는 그 자리를 메운다. 주소를 알아도 이 값을 모르면 못 부르고,
새면 값만 갈면 된다.

**②가 왜 층이 나뉘었나.** 공개 발화가 생기기 전엔 "관리자 아니면 전부 거부" 하나로
충분했다. 이제는 발화마다 다르다 — 관리 발화는 ②를 타고, 공개 발화는 안 탄다.
`tests/chatbot-access.test.js` 가 15개 관리 발화 전부와 공개 발화 2개를 하나씩
확인한다(가드를 하나 빼면 실제로 깨진다).

### CHATBOT_SKILL_KEY 설정 순서 — 순서가 중요하다

**비어 있으면 검증을 건너뛰도록** 만들어 뒀다. 서버에 검증을 먼저 켜고 콘솔에
헤더를 넣으면 그 사이 챗봇이 통째로 죽기 때문이다. 그래서 반드시 이 순서로:

1. 값을 하나 만든다 (임의의 긴 문자열, 32자 이상 권장)
2. **카카오 콘솔** 스킬 설정에 헤더를 넣는다 — `X-Nurungji-Skill-Key: <값>`
   - 콘솔이 커스텀 헤더를 지원하지 않으면 스킬 URL 뒤에 `?k=<값>` 을 붙여도 된다.
     다만 쿼리는 Cloud Logging 의 요청 URL 에 남는다 — 헤더 쪽이 낫다.
3. **Secret Manager** 에 `CHATBOT_SKILL_KEY` 로 같은 값을 넣는다
   (GCP 콘솔 → Secret Manager → 보안 비밀 만들기)
4. Deploy Functions 워크플로 실행

3번과 4번 사이에는 아직 검증이 꺼져 있고, 4번이 끝나는 순간 켜진다.
2번을 먼저 했으므로 카카오는 이미 헤더를 보내고 있다 — 끊기는 구간이 없다.

> 값을 바꿀 때도 같은 순서다. 콘솔 먼저, 그다음 Secret Manager, 그다음 배포.

| 발화 | 하는 일 | 스킬 | 상태 |
|---|---|---|---|
| `도움말` · 폴백 | 지도·등록 안내 카드 | `chatbotHelp` | ⚠️ 콘솔 블록 대기 |

응답하도록 일부러 만들어 뒀다 — 콘솔 설정 전에도 목록은 보여야 하기 때문이다.
대신 처리하려면 목록에 찍힌 `id:` 를 눈으로 보고 발화로 넘겨야 한다.

## 왜 블록 ID가 코드로 돌아와야 하나

버튼을 누르면 "어느 블록으로 보낼지"를 응답에 적어야 한다. 그 블록은 콘솔에서
만들기 전엔 존재하지 않으므로, 순서가 반드시 이렇게 된다:

```
콘솔에서 블록 생성 → 블록 ID 복사 → 설정에 반영 → 재배포 → 버튼 동작
```

인증·팀은 이 ID가 `functions/index.js` 에 상수로 박혀 있고(초기 구현),
신고·클레임은 `functions/.env.nulloongzi-do` 로 뺐다. **새로 설정하는 것은
.env 쪽이라 코드를 건드릴 필요가 없다.**

## ~~남은 작업 1: 신고관리 버튼 붙이기~~ — 2026-09-11 완료

아래는 클레임 쪽을 붙일 때 똑같이 따라가면 되는 기록이다.

### ① 스킬 등록 (2개)

| 스킬명 | 함수 |
|---|---|
| 신고목록조회 | `chatbotReports` |
| 신고처리완료 | `chatbotReportDone` |

등록 후 "스킬 서버 연결 테스트"로 200 OK 확인.

### ② 블록 생성 (2개)

**신고관리**
- 발화: `신고관리`, `신고 관리`, `신고목록`, `신고 목록`
- 봇 응답 → "스킬 데이터 사용" → 스킬: 신고목록조회

**신고처리**
- 버튼 전용(`action: "block"`)이라 발화 패턴은 없어도 된다
- 봇 응답 → "스킬 데이터 사용" → 스킬: 신고처리완료
- 파라미터: `report_id` (string) — 버튼이 `clientExtra` 로 넘기므로 콘솔 설정은
  없어도 되지만, 발화로도 처리하고 싶으면 파라미터로 받도록 열어둔다

### ③ 블록 ID 반영

`신고처리` 블록의 ID를 복사해 `functions/.env.nulloongzi-do` 에:

```
REPORT_DONE_BLOCK_ID=<복사한 블록 ID>
```

(파일에 주석으로 준비돼 있다. `#` 만 떼고 값을 넣으면 된다.)

### ④ 재배포

```
firebase deploy --only functions:chatbotReports,functions:chatbotReportDone --project nulloongzi-do
```

### ⑤ 확인

카카오톡에서 `신고관리` → 카드 목록 + `✅ 처리완료` 버튼이 뜨면 끝.
버튼을 누르면 해당 신고가 `resolved` 로 바뀐다(문서는 지우지 않는다 — "며칠 만에
확인했나"를 나중에 셀 수 있어야 `guidelines.html` 의 영업일 7일 약속을 검증할 수 있다).

## ~~남은 작업 1: 관리자관리 버튼 붙이기~~ — 2026-09-16 완료

구글시트로 접수한 팀들은 등록자가 없어 아무도 정보를 못 고친다. 그 팀의 운영자가
스스로 신청하고, 여기서 사진을 보고 승인한다.

**인증 사진과 요구하는 것이 다르다.** 인증은 "이 팀이 활동한다"를, 관리자 신청은
"내가 이 팀 사람이다"를 보여야 한다. 공개된 인스타 사진은 앞의 것만 증명하므로
증빙이 되지 않는다 — 신청 화면이 단톡방 캡처 등을 예로 든다.

### ① 스킬 등록 (3개)

| 스킬명 | 함수 |
|---|---|
| 관리자신청목록 | `chatbotAdminRequests` |
| 관리자승인 | `chatbotAdminApprove` |
| 관리자거절 | `chatbotAdminReject` |

### ② 블록 생성 (3개)

**관리자관리** — 발화: `관리자관리`, `관리자 관리`, `권한관리` / 스킬: 관리자신청목록
**관리자승인** · **관리자거절** — 버튼 전용. 스킬만 연결한다

### ③ 블록 ID 반영

```
ADMIN_APPROVE_BLOCK_ID=<관리자승인 블록 ID>
ADMIN_REJECT_BLOCK_ID=<관리자거절 블록 ID>
```

승인 ID만 있어도 승인 버튼은 붙는다(거절 버튼만 빠진다).

### ④ 재배포 후 `관리자관리` 로 확인

카드에 `🔍 사진 크게 보기`가 함께 뜬다. 단톡방 캡처처럼 세로로 긴 사진도
잘리지 않게 `fixedRatio` 를 켜뒀다.

> **콘솔 작업에서 겪은 것(2026-09-16).**
> - 스킬 연결 테스트가 `Request timeout to bot-proxy.daumkakao.io ... after 5000 ms`
>   로 한 번 실패했다. 콜드스타트다 — 재시도하면 붙는다.
> - 테스트 응답 본문이 `⛔ 권한이 없습니다` 여도 정상이다. 콘솔 테스트에는 카카오
>   사용자 ID 가 실리지 않아 `admin_kakao_ids` 검사에서 걸린다. 연결 자체는 된 것.
> - 콘솔은 HTTP 상태코드를 보여주지 않는다. `[INFO] 올바른 스킬 서버 응답입니다`
>   문구가 성공 신호다.
> - 승인/거절 블록에 **파라미터를 만들 필요가 없다.** 버튼이 `clientExtra` 로
>   `request_id` 를 넘긴다.

## ~~남은 작업: 클레임관리 버튼 붙이기~~ — 2026-09-16 완료

같은 절차다.

### ① 스킬 등록 (3개)

| 스킬명 | 함수 |
|---|---|
| 클레임목록조회 | `chatbotClaims` |
| 클레임승인 | `chatbotClaimApprove` |
| 클레임거절 | `chatbotClaimReject` |

### ② 블록 생성 (3개)

**클레임관리**
- 발화: `클레임관리`, `클레임 관리`, `소유권관리`
- 스킬: 클레임목록조회

**클레임승인** / **클레임거절**
- 버튼 전용. 스킬만 연결한다
- 파라미터(선택): `claim_id` (string)

### ③ 블록 ID 반영

```
CLAIM_APPROVE_BLOCK_ID=<클레임승인 블록 ID>
CLAIM_REJECT_BLOCK_ID=<클레임거절 블록 ID>
```

`CLAIM_APPROVE_BLOCK_ID` 만 있어도 승인 버튼은 붙는다. 거절 ID가 없으면 승인
버튼만 나온다 — 둘 다 넣는 걸 권한다.

### ④ 재배포 후 `클레임관리` 로 확인

> **`claim_id` 파라미터는 여기서만 의미가 있다(2026-09-16).**
> 관리자 쪽(`extractRequestId`)은 clientExtra 가 비면 **발화 마지막 토큰**을 id 로
> 읽는 폴백이 있지만, 클레임 쪽(`resolveClaim`)은 `clientExtra.claim_id ||
> params.claim_id` 만 본다. 그래서 콘솔 파라미터가 실제 폴백 경로가 된다.
>
> 콘솔에서 엔티티 선택지는 `@sys.text`(임의의 텍스트)와 `@sys.constant` 둘뿐이라
> **`@sys.text`** 로 잡는다. **'필수 파라미터로 설정'은 체크하지 않는다** — 버튼이
> clientExtra 로 넘기므로, 필수로 두면 봇이 값을 되묻는 단계가 끼어든다.
>
> 클레임 카드에는 증빙 사진이 없다. 팀 이름 + 가린 메일 + 신청일만 나오고
> 썸네일은 누룽지도 로고다. 판단 근거가 "시트에 적힌 담당자 메일과 같은 주소로
> 가입했다" 하나뿐이기 때문이다.

## 남은 작업: 공개 발화 블록 만들기

서버는 배포돼 있고 콘솔 블록만 없다. 블록이 없으면 사용자가 아무 말이나 했을 때
기본 폴백("무슨 말인지 모르겠어요")이 나간다.

### ① 스킬 등록 (2개)

| 스킬명 | 함수 |
|---|---|
| 길잡이 | `chatbotHelp` |
| 제보접수 | `chatbotPublicReport` |

### ② 블록 생성 (2개)

**도움말**
- 발화: `도움말`, `안녕`, `누룽지도`, `지도`, `사용법`
- 스킬: 길잡이
- **폴백 블록으로도 지정한다** — 아무 말이나 했을 때 여기로 오게. 이게 이 기능의
  절반이다. 사람들은 정해진 명령어를 외워서 오지 않는다.

**제보**
- 발화: `제보`, `제보하기`, `정보수정`, `정보 수정`, `오류신고`
- 스킬: 제보접수
- 파라미터 불필요 — 서버가 발화 전체(`userRequest.utterance`)를 받아 앞의 키워드만
  떼고 나머지를 내용으로 본다.

### ③ 배포 후 확인

운영자가 아닌 계정으로 `도움말` → 지도 카드가 나오면 된다.
`제보 테스트입니다` → 접수 응답 + `신고관리` 목록에 `[카톡 제보]` 로 뜬다.

## 알아둘 것

- **응답 5초 제한.** Cloud Functions 콜드스타트가 겹치면 첫 호출이 넘길 수 있다.
  한 번 더 보내면 붙는다.
- **관리 발화는 관리자만.** `admin_kakao_ids/{kakao_user_id}` 문서가 있어야 한다.
  남이 발화하면 "권한이 없습니다"로 끝난다. 공개 발화(도움말·제보)는 이 검사를
  타지 않는다.
- **제보에 답장할 수단이 없다.** 카카오 채널에서 먼저 말을 거는 건 별도 API·비용이
  필요하다. 그래서 접수 응답이 "따로 답장드리진 못해요"를 먼저 말한다 —
  안 알리면 사람들이 기다린다.
- **제보자의 카카오 user id 를 `reporter_kakao_id` 로 남긴다.** 같은 사람이 반복
  제보하는지 보려는 것이고, 그 값으로 개인을 식별할 수단은 우리에게 없다.
- **`⚠️ 알림 미발송 N건`이 목록 맨 위에 뜨면** 카카오 토큰이 죽은 것이다.
  신고는 접수됐는데 카톡이 안 갔다는 뜻이라, 토큰부터 살려야 한다
  (2026-09-08 KOE322 장애 참고).
- 카톡 알림의 '자세히 보기'는 해당 팀/픽업으로 바로 간다. 운영자 폰에 앱이
  깔려 있으면 App Links 로 앱이 열린다.
