## 2. 제품 구조 (코드 기준)

### 웹 (`null_oongzi-do`)

Vanilla JS · classic script · `window.*` 전역 통신 · Firebase compat SDK. ES module 아님.
`index.html`이 셸이고 `js/*.js`가 기능별 모듈. 상세는 `CLAUDE.md` 참조.

### 앱 (`null_oongzi-do-app`)

Flutter 네이티브. 지도는 **flutter_naver_map**(웹은 카카오맵). 화면·위젯 구조는 웹을 포팅한 것이며
기능 대조표는 앱 레포 `docs/feature-parity.md`에 있다.

### 두 플랫폼이 공유하는 것

Firestore 스키마, Firestore 보안 규칙, Cloud Functions, 애널리틱스 이벤트 이름.
**한쪽을 고치면 다른 쪽 패리티를 확인하라.** 2026-09-02~03 감사에서 등록 폼에만 15건의
불일치가 나왔다(대부분 수정 완료).

## 5. 진짜 남은 갭

§3을 걷어내고 실제로 비어 있는 것만 남긴 목록이다.

### 5-1. 제3자 신고 경로가 UI에 없다 ★

- **현재**: 시딩된 픽업 크루에는 상세 화면에 takedown mailto 링크가 있다. 하지만 **동호회에는
  "정보가 틀렸어요" 버튼이 없다.** 이메일 주소는 `guidelines.html`·`terms.html`에만 적혀 있다.
- **왜 문제**: 남이 등록한 정보가 틀렸을 때 앱 안에서 신고할 방법이 없다. 정책 문서에
  "7일 내 확인"을 약속해 두고 창구는 문서 안에만 있는 상태.
- **최소 구현**: 동호회·픽업 상세 하단에 "정보가 틀렸어요" → 항목 id·이름이 프리필된 mailto.
  시딩 크루 takedown 링크와 같은 패턴을 재사용하면 된다.

### 5-2. 데이터 신뢰도 필드가 없다

- **현재**: `clubs` 문서에 최종 확인일이나 상태 필드가 없다. 해체된 팀, 바뀐 연습 시간을
  구분할 방법이 데이터에 없다.
- `guidelines.html`에 "6개월마다 점검, 30일 무응답 시 표시 중단"을 적어뒀는데
  **그걸 기록할 자리가 스키마에 없다.** 문서가 앞서 있고 구현이 따라가야 하는 상태.
- **제안 스키마**:
  ```
  clubs/{id}
    last_verified_at: timestamp   // 최종 확인일
    source: 'self' | 'curated'    // 자발적 등록 | 운영자 시딩 (픽업엔 이미 있음)
    status: 'active' | 'needs_check' | 'dormant'
  ```
- `needs_check`는 **숨기지 말고 드러낼 것.** "최종 확인 8개월 전" 같은 표시가 신뢰를 만든다.

### 5-3. 갱신 운영이 수작업이다

점검 대상을 뽑아주는 것이 없다. 5-2가 들어가면 "6개월 지난 팀 목록"을 쿼리로 뽑을 수 있다.

### 5-4. 내부 대시보드가 없다

총 팀 수, 지역 분포, 갱신율, 신규 등록 추이, NSM 추이. 공개 불필요, 운영자 본인용.
Firebase Analytics 콘솔로 일부는 보이지만 갱신율은 5-2 없이는 계산 불가.

### 5-5. 링크트리 APK 링크 (코드 밖)

초판 지적 사항. 리포에서 확인 불가하나 사실이면 5분 작업이고 구버전 배포를 막는다.
**확인 후 Play Store 링크로 교체할 것.**

### 5-6. 픽업에 길찾기 버튼이 없다

NSM이 "주당 길찾기 클릭 수"인데 픽업 상세에는 주소 복사만 있고 길찾기가 없다.
좌표가 있는 크루에는 붙일 수 있다. 붙이면 NSM 분모가 넓어진다.

## 7. 가드레일 (2026)

> 원칙: **시간과 콘텐츠는 넣되, 돈과 사람은 넣지 않는다.**

- **수익화 기능을 붙이지 말 것.** 결제·광고·구독·유료 노출 전부 2027 이후. 지금은 데이터 밀도가
  부족해 값이 안 나온다. (`terms.html` 제3조에 "유료화 시 30일 전 고지, 기존 등록물 소급 유료화
  없음"을 이미 박아뒀다.)
- **유료 인프라로 확장하지 말 것.** 무료 티어로 감당되는 규모다. 서버 비용이 생기는 순간
  수익화 압박이 따라온다.
- **공동 개발자·지분 합류를 서두르지 말 것.** 역할과 지분을 문서로 정하지 않은 합류가 가장 큰 리스크다.
  도움이 필요하면 **범위가 정해진 단발 협업**으로 받을 것.
- **위볼리 기능을 따라가지 말 것.** 회원관리·출석·회비는 남의 땅이다.
- **대규모 리라이트를 하지 말 것.** 웹앱도 앱도 작동한다. 남은 건 문서와 작은 폼과 필드 몇 개다.
- **§3을 다시 만들지 말 것.** 이번 개정의 이유다.

## 9. 운영자 질문 — 답변된 것

| 연락처 공개? | 등록자가 입력한 인스타 핸들·단톡 링크를 공개. opt-in 등록이므로 동의 전제 |

## 부록 A — 우선순위의 배경 (선택)

초판의 P0가 전부 "틀 만들기"였던 근거는 운영자의 명리 상담이었다.
명조 己卯 丙寅 丙申 庚寅(편인격)에서 오행이 금(金)→수(水)에서 끊긴다 —
배우고(木 37.5%) 만들고(火 25%) 결과를 내는(金 25%) 힘은 강한데,
담고 멈추고 규칙을 세우는 축(水 0%)이 비어 있다는 해석이다.

**실사 결과 이 진단은 절반 맞았다.** 약관과 운영 기준은 실제로 없었고 2026-09-03에 채워졌다.
그러나 개인정보처리방침·삭제 경로·성과 지표는 이미 있었다. 즉 "담는 축이 통째로 비었다"는
과장이었고, **"관성이 약하다"** 정도가 사실에 가깝다.

배경으로 알아둘 가치는 있으나 **실행 판단은 §5의 실측 갭으로 하면 된다.**
2026년 가드레일(돈·사람 투입 자제)은 명리 근거와 별개로 제품 논리로도 성립한다 —
데이터 밀도가 부족한 단계의 수익화는 값이 안 나오고, 문서화되지 않은 합류는 실제로 최대 리스크다.
